# 《Kimi剧本锚点化执行指南》分析评估与优化执行方案

> 日期：2026-08-13 ｜ 分析对象：`Kimi剧本锚点化执行指南.md`（Qoder CN 编写）
> 结论先行：**指南的省 Token 思路在"纯聊天窗口"场景下成立，但它假设的执行环境（人工搬运产物、长上下文免费驻留、200 章单段输出）与 Kimi Work 实际能力不匹配；在 agent 环境下应改为「预处理切分 + 逐槽消化 + 机器校验 + 自动落盘」流水线，成本更低、保真更高、可断点续跑。**

---

## 一、现状核实（2026-08-13 实测，指南未提及的关键事实）

| 事实 | 证据 | 对指南的影响 |
|------|------|--------------|
| 56 个摘要槽已存在，但只是**章目占位**（章号+标题+字数），summary 区待填 | `digest-0001-0050.md` 头部自注"summary 待 Kimi 长上下文填充" | 产出应**直接回填进 56 槽**，不是另存 13 份 txt 再合并 |

## 二、指南逐条评估

### 2.1 合理、应保留的设计

- 固定输出格式（事件链/境界/人物/伏笔/接力摘要）——程序可解析，好
- 忠实原文红线 + 「待考」兜底 + 伏笔宁缺毋滥——质量纪律正确
- 接力摘要替代回读——思路正确（但载体应改，见下）
- 失败只补缺段——方向正确（但"段"粒度太大，见 2.2-②）

### 2.2 五个结构性问题

**① "长上下文驻留=省钱"是计费错觉。**
按卷开会话后，会话内每发一轮请求，**整卷 110 万字 + 已产出内容都要随上下文重传计费**。产第 3 段时，前两段输出和整卷原文在每一轮里重复计价。"边际成本极低"只在不计量上下文的包月聊天场景成立；在 API/agent 计量场景恰恰相反——**上下文越小越省**。

**② 200 章单段输出过长，中断风险与重试成本双高。**
单段输出 8–12K 字（200 行事件链+三节），已贴近单次回复输出上限，恰是指南第 44 行预设"输出中断"的原因；一旦中断，重试单位是 200 章。

**③ 整卷驻留的保真度衰减直接冲击"忠实原文"红线。**
模型对百万字级上下文的中后部细节召回质量会下降（lost-in-the-middle），而本任务的输出恰恰是逐章事实提炼——保真度就是产品质量。

**④ 人肉管道环节过多。**
"用户保存每段为 txt → 命名 kimi-ch*.txt → 交回 Qoder → 脚本合并进 56 槽"：13 次人工搬运 × 命名 × 拆分，任一环节出错污染全链。旧批次文件的错章号就是前车之鉴。接力摘要跨 6 个会话怎么传递，指南也没说——实际还是靠人复制。

**⑤ 无机器校验回路。**
章号准确、缺章跳过、覆盖率、[收]伏笔的埋设章引用有效性，全靠模型自觉。结构化数据不经过程序化验收就入锚点库，错误会沉淀进游戏。

## 三、优化执行方案：四段流水线（推荐）

```
Step 0  预处理切分（Python，一次性，零模型成本）
Step 1  逐槽消化 ×56（模型，每槽独立上下文，断点续跑）
Step 2  机器校验（Python，每槽即验，不合格进重做队列）
Step 3  锚点合成（Python，56 槽 → anchors.json 自动合并）
```

### Step 0：预处理切分（Python 脚本，一次跑完）

- 按 `第N章` 正则切分 6 卷原文 → **56 个槽位原文包** `chunks/ch0001-0050.txt` …（对齐现有 digest 槽粒度，消灭粒度错配）
- 同时产出 `manifest.json` 并自动对账：
  - 总章数 = 2704；缺章 = {2663, 2667}（与 chapters.json 的 `gaps_after` 核对）
  - 每章字数 vs chapters.json 的 `len` 字段逐章对账（容差 ±5%）
  - 末卷实际起始章验证（指南提到 2501 卷实从 2499 起——用程序确认而不是靠人记）
- 对账失败即报出具体章号清单，**先把源数据问题暴露在第 0 步**

### Step 1：逐槽消化（56 槽循环）

每槽一个独立工作单元：

1. 读 `chunks/ch{起}-{止}.txt`（约 50 章 × 2400 字 ≈ **12 万字**，处于高保真上下文区间）
2. 读 `state.json`（接力状态机：当前境界 / 活跃人物表 / 未回收伏笔清单，机器可读）
3. 按指南第三节格式生成摘要，**直接写入** `chapters/digest-{起}-{止}.md`（保留槽内已有章目区，追加/替换 summary 区）
4. 程序把该段的接力摘要解析回 `state.json`，`progress.json` 标记该槽 done

特性：

- **断点续跑**：任何中断，重跑 = 单槽 50 章；跨会话零负担（状态在文件里，不在对话里）
- **上下文恒定小**：每槽输入 ≈ 12 万字 + 2K 字状态，无长上下文衰减
- 56 槽可分多天执行，可挂 Automation 定时任务（如每晚 8 槽，7 天跑完）

### Step 2：机器校验（Python，随跑随验）

对每份 digest 自动检查：

| 检查项 | 规则 |
|--------|------|
| 覆盖率 | 事件链行数 == 槽内实际章数（自动跳过缺章） |
| 章号连续 | 事件链章号集合 == manifest 该槽章号集合 |
| 格式齐全 | 事件链/境界/人物/伏笔/接力五节齐备 |
| 伏笔引用 | 每条 [收] 的"对应埋设章"存在于已登记 [埋] 或标「待考」 |
| 忠实抽查 | 每槽随机抽 3 章，事件描述中的专有名词须出现在原文该章（词级校验） |

不合格槽 → `redo-queue.json`，重跑仅涉及这些槽。

### Step 4（即 Step 3）：锚点合成

- 解析 56 份 digest 的事件链 + chapters.json 的 kw → 生成 `anchors.json`
- 字段映射：chapter=章号，title=章标题，keywords=chapters.json.kw ∪ 事件行实体，trigger=触发条件列，summary=事件列，refs=关联伏笔章
- 格式严格对齐现有空脚手架（anchor-v1），Qoder 侧零改动接入

### 成本与质量对比

| 维度 | 指南方案（6 会话×整卷驻留） | 流水线方案 |
|------|------------------------------|------------|
| 模型输入总量 | 6 卷驻留 + 会话内每轮全量重传（计量场景约为全文的 2–3 倍） | 全文恰好一遍（56×12 万字）+ 状态文件 ~1% |
| 单点故障重试粒度 | 200 章/段 | 50 章/槽 |
| 忠实度 | 长上下文中后部衰减风险 | 每槽高保真区间 + 机器抽验 |
| 人工操作 | 13 次保存/命名/交回 + 跨会话复制接力摘要 | 0（启动后自动落盘，可选定时调度） |
| 校验 | 无 | 5 项机器校验 + redo 队列 |
| 与现有骨架兼容 | 需另写"段→槽"拆分合并脚本 | 原生对齐 56 槽 / anchors.json 格式 |

## 四、迁移说明（指南中应原样保留的部分）

- 第三节输出格式 → 作为 Step 1 的生成契约，一字不改
- 第四节质量红线 → 写入 Step 1 每槽的生成指令 + Step 2 机器校验兜底
- 缺章跳过规则 → 已在 Step 0 的 manifest 中程序化

**一句话：指南解决的是"怎么让 Kimi 在聊天窗口里干这活"；流水线解决的是"让这活像构建工程一样可重复、可校验、可续跑"。两者不冲突——流水线 = 指南的格式契约 + 工程化执行外壳。**
