# 《系统赋我长生》迭代规划 v0.4（Kimi 优化版）

> 日期：2026-08-12 ｜ 基线：v0.3（P1/P2 已完成）｜ 作者：Kimi Work
> 本文档为 v0.3 的增量优化，不推翻原有架构与裁决点（R1–R6 全部保留）。

---

## 一、对 v0.3 的诊断（为什么要优化）

| v0.3 问题 | 影响 | v0.4 对策 |
|-----------|------|-----------|
| P3 单批过大（7 个子系统一锅出，~14k token） | 批中出错难以定位，验收粒度粗 | 拆为 **P3a / P3b** 两个子批，每批独立验收 |
| 验证依赖"浏览器实玩"，无自动化 | 手工回归成本高，批间易回归 | 新增 **T0 测试基座**：Node 无头断言（DOM stub），每批必过 |
| README 记载"本机无 node"已过时 | 测试手段受限 | 运行时已提供 Node v24；游戏本体仍零依赖、build.py 仍为 stdlib，Node 仅用于测试，不进产物 |
| 存档版本策略只到 v2 | P3 新增背包/功法/状态等字段 | 存档升级 **v3**，迁移链 v1→v2→v3，沿用零漂移原则 |
| 条件表达式 item/rep 只是预留 | P3 内容无法引用背包/势力 | P3a 第一件事就是**接通 item/rep 条件**，后续内容全部数据驱动 |
| P4–P6 验收标准偏笼统 | 批尾难以判定完成 | 每批补**可执行验收断言清单**（Node 测试即验收） |
| P5 中"AI 增强（Ollama）"依赖外部环境 | 阻塞批次交付 | 降为 P5 内**可选开关项**，不阻塞 P5 验收；静态内容库保底（沿用 R3） |

## 三、P3 技术设计（本批执行依据）

### 3.1 存档 v3 新增字段（v2→v3 迁移补默认，零漂移）

```
gs.inventory   = {}   // 消耗品/材料 {物品名: 数量}
gs.ownedEquips = []   // 持有装备名列表（gs.equip 仍为当前装备）
gs.statuses    = []   // [{id,name,years,delta:{...}}] 持续状态，passYear 时 tick
gs.reputation  = {}   // 势力声望 {势力: 数值}
gs.arts        = {}   // 已习功法 {id: 层数}
gs.talent      = null // 命格 id（开局三选一）
gs.mp          = 当前灵力（mpmax 派生：20 + 神魂×1 + 灵力属性×2）
```

### 3.2 新模块划分（沿用"引擎层/内容层"分离）

```
js/data/items.js     物品/配方配置表（内容层）
js/data/arts.js      功法/命格配置表（内容层）
js/data/factions.js  势力配置表（内容层）
js/inventory.js      背包/换装/使用物品（引擎层）
js/buff.js           状态 tick（挂入 passYear）（引擎层）
js/arts.js           功法习得/技能释放/渡劫节点（引擎层）
js/faction.js        声望增减/阵营判定（引擎层）
js/encounter.js      奇遇事件（条件驱动，内容+引擎）
```

### 3.3 关键约束（不可破坏，沿用 v0.3 + 新增）

- 一切数值进 data/ 配置表，不写死公式
- AI 只做填充，主线/结局锁定（R3）
- 游戏本体零依赖，Node 仅测试用，不进 dist
- 每批交付：dist 可玩 + Node 断言全绿 + 验证记录
- **工程副本原则**：Kimi 工作副本位于 `D:\AI-Kimi\全流程游戏开发\longlife-mud\`，原工程 `D:\AI-app\longlife-mud\` 不动
